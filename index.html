01 / EXECUTIVE SUMMARY

執行摘要

本次練習以老師律定並授權的 PHP2Shell Lab 為目標（目標網址：http://lab.feifei.tw:8101/），核心主題為 CVE-2026-109618 與 CVE-2026-109619 所涉及之 PHP 請求處理與 multipart/form-data 相關 Heap Use-After-Free（堆積記憶體釋放後使用）風險。

白話版：當伺服器接收檔案上傳時，PHP 開啟了「上傳進度追蹤」功能，會在接收到請求瞬間自動將進度資訊寫入 Session 暫存檔；若伺服器允許客戶端自訂 Session ID（session.use_strict_mode=0），攻擊者就能預知並控制 Session 檔案名稱，將惡意 PHP 程式碼寫入磁碟。最後透過網站上的 view.php 檔案包含漏洞（LFI），讓伺服器載入並執行該 Session 檔案，一舉奪得遠端指令執行權限（RCE）。

透過編寫自動化 Python 滲透腳本，已實測完成 Session Injection → LFI → RCE 完整攻擊鏈，並成功自目標系統取得驗證 Flag：

證據核實：本次報告具備完整的 HTTP 封包交互記錄、Python 自動化 Exploit 原始碼、/var/www/html/check_flag.php 原始碼比對、以及利用 /proc 動態提取之行程與環境變數記錄。實測證實只要 Session 注入與 LFI 漏洞組合成立，即使未深度觸發底層 UAF 記憶體損毀，也能在 PHP 身分下達成 100% 可重現的 RCE。

先看名詞：本報告用到的關鍵術語字典
  • Session（會話）：伺服器為每位訪客保存狀態（如登入身分、購物車）的機制，預設以文字檔案儲存在伺服器端（如 /var/lib/php/sessions/sess_{ID}）。
  • Session ID：瀏覽器與伺服器用來指認特定 Session 的隨機識別碼，通常存於 Cookie 的 PHPSESSID。
  • Session Upload Progress：PHP 提供的功能。當表單帶有指定欄位時，PHP 會在背景自動記錄上傳進度至 Session，無需等檔案完全傳輸結束。
  • LFI（本地檔案包含）：應用程式未嚴格過濾輸入，直接將使用者傳遞的路徑傳給 include() 或 require()，導致伺服器載入非預期的本地檔案。
  • RCE（遠端程式碼執行）：攻擊者能跨越網路在目標伺服器執行任意系統指令或程式碼，屬最高危險性弱點。
  • UAF（Use-After-Free）：軟體釋放記憶體指標後未清空，後續指標被再次存取，造成記憶體資料混亂或控制流劫持。
  • /proc 虛擬檔案系統：Linux 核心動態產生在記憶體中的介面，透過檔案形式暴露目前所有系統行程（PID）、指令行與環境變數。
  • flag：靶機課程中用於證明已攻破目標或取得特定系統權限的字串標記。

04 / TECHNICAL FINDINGS

漏洞技術分析

本靶機核心弱點由「記憶體缺陷風險 + 脆弱 PHP 設定 + 應用層檔案包含」三重弱點連鎖形成，單一防線失守即導致全盤控制：

F-01 · MEMORY SAFETYCritical

PHP multipart/form-data Heap UAF

原理：CVE-2026-109618 涉及 OOM（記憶體耗盡）異常中斷時造成的無效指標；CVE-2026-109619 涉及 PHP 工作行程保留已過期的跨請求全域狀態。官方公告確認受影響版本包含 PHP 8.3.35。

影響：在特殊記憶體排布下可被操縱實現記憶體任意寫入與控制流劫持。官方來源：GHSA-w8hw-w9fx-j79w。

狀態：官方缺陷已確認；本實驗主要展示更具穩定性之應用組合利用鏈。

F-02 · SESSION INJECTIONHigh

session.upload_progress.enabled 未停用

原理：PHP 預設開啟上傳進度追蹤。當 POST 包含 multipart/form-data 且表單帶有 PHP_SESSION_UPLOAD_PROGRESS 欄位時，PHP 會在接收到資料的第一時間將該欄位值寫入對應的 Session 檔案中。

影響：允許攻擊者繞過正常的業務邏輯，直接將任意字串（包含 PHP 標籤 <?php ... ?>）寫入伺服器檔案系統。

狀態：實測利用成功，已確認為可穩定寫入惡意代碼之資料通道。

F-03 · PREDICTABLE TARGETHigh

session.use_strict_mode = 0 未啟用嚴格模式

原理：當 session.use_strict_mode = 0 時，伺服器允許客戶端在 Cookie 中任意指定未經初始化的 PHPSESSID（例如 PHPSESSID=getflag123），伺服器將直接採納並建立 sess_getflag123 檔案。

影響：攻擊者完全掌握儲存檔案的實體路徑與檔名，大幅消除盲猜路徑的難度。

狀態：實測利用成功，可精確控制 Session 檔案名稱。

F-04 · CODE EXECUTIONCritical

view.php 本地檔案包含（LFI to RCE）

原理：view.php 接收使用者傳入之 file 參數，未經過濾即直接呼叫 include($_GET['file'])。PHP 會把包含檔案中的內容當成 PHP 腳本解析執行。

影響：將原本僅作為進度暫存的文字 Session 檔案提升為可執行程式碼，直接升級為 RCE。

狀態：實測利用成功，成功執行系統指令並取得 Flag。

08 / REMEDIATION

修補與安全加固建議

1. 升級 PHP 核心版本（根本解決記憶體安全問題）

盡速將 PHP 升級至官方安全更新版本（PHP 8.3.36、8.2.35 或 8.4.27 以上），修補 multipart/form-data 處理時的 Heap Use-After-Free 弱點，消除底層記憶體損毀風險。

2. 強化 Session 安全組態（消除 Session 注入通道）

在 php.ini 中修改組態設定，阻斷透過上傳進度與偽造 ID 寫入惡意檔案：

; 1. 若無即時上傳進度條需求，直接停用該功能（強烈建議）
session.upload_progress.enabled = Off

; 2. 啟用 Session 嚴格模式，強制拒絕未經伺服器初始化的自訂 Session ID
session.use_strict_mode = On

; 3. 限制 Session ID 僅能來自 Cookie，阻斷 URL 傳遞
session.use_only_cookies = On

; 4. 設定 Cookie 安全標頭
session.cookie_httponly = On
session.cookie_samesite = Lax

3. 修復 view.php 檔案包含邏輯（防禦縱深）

禁止將客戶端參數直接傳入 include() 或 require()。改採伺服器端白名單映射：

<?php
// 安全實作範例：白名單字典映射
$allowed_pages = [
    'home'  => 'templates/home.php',
    'about' => 'templates/about.php',
];

$page = $_GET['page'] ?? 'home';

if (array_key_exists($page, $allowed_pages)) {
    include($allowed_pages[$page]);
} else {
    http_response_code(404);
    echo "找不到指定頁面";
}
?>

結論與學習重點

本次 PHP2Shell Lab 完整展示了現代 Web 安全中最典型的「缺陷連鎖（Vulnerability Chaining）」：個別看似次要的組態弱點（未關閉上傳進度、未開啟 Session 嚴格模式），一旦與應用層缺乏過濾的檔案包含（LFI）結合，就能在不需暴力破解或高度複雜記憶體堆疊佈局的情況下，達成危害度極高的遠端程式碼執行（RCE）。

學完這份報告，可以帶走的三大核心安全思維：
  1. 資料與程式碼必須嚴格分離：使用者能間接或直接影響的內容（如 Session 儲存的表單進度），絕不能流入具備程式執行語意的排程或包含通道中。
  2. 單一弱點不可怕，組合連鎖才致命：防禦縱深（Defense in Depth）的真諦在於切斷任何一個環節（停用 Upload Progress、開啟 Strict Mode 或白名單包含），攻擊鏈就會立即瓦解。
  3. 版本更新與安全組態缺一不可：修補核心漏洞的同時，必須同步收斂不需要的系統功能；移除指令列工具無法替代權限隔離。
