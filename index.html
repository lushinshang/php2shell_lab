01 / EXECUTIVE SUMMARY

摘要

本次練習以老師律定並授權的 PHP2Shell Lab 為目標，主題為 CVE-2026-109618／CVE-2026-109619 所涉及的 PHP 請求處理記憶體安全問題，包含 multipart/form-data 相關的 Heap Use-After-Free（堆積記憶體釋放後使用）風險。

白話版：網站接收檔案上傳時，PHP 內部的記憶體處理有缺陷；再加上兩個設定疏忽，攻擊者就能把一段資料寫進伺服器，並讓網站把它當成程式執行。下面的章節會一步一步拆解這條路徑。

依學員提供的練習結果，透過 Session Injection → LFI → RCE 利用鏈取得 PHP 執行環境中的程式碼執行能力，並完成 flag 讀取驗證。本文僅保留遮蔽後的結果：

證據界線：本報告依題目與學員敘述整理；未提供封包、畫面、原始碼或執行日誌，也未由本次文件製作程序連線重測。取得 flag 為學員回報結果；各項設定與 LFI 尚待原始證據核對。Session 注入加上 LFI 可獨立形成 RCE，不能以此結果直接認定兩項 CVE 均已實際觸發。

先看名詞：本報告用到的關鍵術語
  • Session（會話）：伺服器為每位使用者保存狀態（例如是否已登入）的機制，資料通常存放在伺服器的檔案裡。
  • Session ID：用來辨認某一段 Session 的識別碼，瀏覽器通常透過 Cookie 送出。
  • LFI（本地檔案包含）：程式把伺服器上的某個檔案「載入並解讀」，而該檔案的路徑可以被使用者影響。
  • RCE（遠端程式碼執行）：攻擊者能讓目標伺服器執行自己指定的程式或指令，是最嚴重的一類風險。
  • UAF（Use-After-Free）：程式釋放記憶體後仍繼續使用該區域，可能被利用來改變程式的行為。
  • Heap（堆積記憶體）：程式執行時動態配置記憶體的區域；UAF 多半發生在這裡。
  • PHP-FPM：實際負責執行 PHP 程式碼的服務行程，Nginx 會把請求轉交給它。
  • flag：課程用來證明「已完成某個步驟」的字串。本報告一律以 flag{REDACTED} 遮蔽。

04 / TECHNICAL FINDINGS

漏洞分析

以下嚴重度為本靶機利用鏈的情境評估；設定開啟本身不等同於獨立的高風險漏洞。未另行計算各項 CVSS 分數。

F-01 · MEMORY SAFETYCritical

PHP multipart/form-data Heap UAF

原理：CVE-2026-109618 涉及記憶體不足（OOM）中斷造成無效狀態；CVE-2026-109619 涉及工作行程保留已失效的跨請求狀態。multipart 處理可成為相關觸發面，兩者並非同一個缺陷。

影響：適當條件下可導致 PHP 工作行程身分的 RCE。官方對 OOM 案例的完整驗證以 mod_php 為主，不能直接推定本 Lab 的 FPM 已完成相同利用。OOM 來源／狀態殘留來源。

偵測與處置：關聯 multipart 請求、OOM、FPM 異常退出及重啟；優先升級。狀態：版本風險待核對，UAF 實際觸發未獨立確認。

F-02 · SESSION WRITEHigh

session.upload_progress.enabled 未關閉

原理：上傳進度功能可在上傳處理期間，把請求衍生的進度資料寫入 Session。若採檔案式儲存，便可能形成包含不受信任內容的本地檔案。參見 PHP 上傳進度手冊。

影響：與可控 Session ID、可讀取的儲存位置及 LFI 組合後，才可能將資料轉為可執行內容；開啟此功能本身不代表 RCE。

偵測與處置：比對異常上傳與 Session 檔案變更；無需求即停用。狀態：依題目列入，尚缺執行環境設定佐證。

F-03 · SESSION TRUSTHigh

use_strict_mode=0 允許偽造 Session ID

原理：正確設定名稱為 session.use_strict_mode。關閉時，PHP 可接受客戶端指定、尚未初始化的 Session ID，增加 Session 固定及可預測儲存目標的風險。這不等同於自動取得他人的登入狀態。參見 PHP 設定說明。

影響：降低 Session 注入鏈的定位難度；仍受儲存處理器與權限限制。

偵測與處置：觀察由客戶端指定的新 ID 與異常建檔，日誌避免記錄完整 Session ID；啟用嚴格模式。狀態：依題目列入，待核對有效設定與實際行為。

F-04 · FILE INCLUSIONCritical

view.php 本地檔案包含（LFI）

原理：網站本來應該只載入固定的頁面模板。但如果使用者的輸入能決定 include／require 要載入哪個本地檔案，程式就可能去讀一個原本不該碰的檔案，例如 Session 檔案。

影響：當檔案含有能被 PHP 解譯的內容時，LFI 可升級為 RCE；若只是讀取文字而非執行包含，則不能直接推定程式碼執行。

偵測與處置：關聯 view.php 的異常路徑、包含失敗錯誤及 Session 存取；改用固定模板映射。狀態：學員回報鏈成立，待原始碼或去識別化回應佐證。

05 / ATTACK CHAIN

攻擊鏈與利用流程

下圖示意 Session 資料寫入、LFI 包含與 PHP 執行的責任順序；view.php 為 PHP-FPM 內執行的應用邏輯，圖中獨立列出以凸顯信任邊界。

    autonumber
    actor A as 攻擊者
    participant N as Nginx
    participant P as PHP-FPM
    participant F as 檔案系統
    participant V as view.php
    Note over A,V: 授權 Lab 示意；不包含可執行 payload
    A->>N: 上傳請求，帶入指定 Session 識別與示意資料
    N->>P: 轉交 multipart 請求
    P->>P: 解析上傳，處理 Session 與進度資料
    P->>F: 將請求衍生內容寫入 Session 檔案
    Note over P,F: Session Injection：資料仍須存在且可被讀取
    A->>N: 請求 view.php，影響待包含的本地資源
    N->>P: 轉交檢視請求
    P->>V: 執行應用的檔案包含邏輯
    V->>F: LFI 讀取指定的 Session 檔案
    F-->>V: 回傳含示意程式片段的內容
    V->>P: 以 PHP 包含語意解譯內容
    Note over P,V: RCE：沿用 PHP 工作行程權限
    P->>F: 最低限度環境探勘與授權 flag 讀取
    F-->>P: 驗證資料
    P-->>N: 驗證回應
    N-->>A: 確認結果，報告僅保留遮蔽 flag

成立條件：此示意假設檔案式 Session 儲存、內容寫入後仍存在、PHP 可讀取該檔，且 view.php 使用包含語意。上傳進度清理、請求時序、Session 鎖定與 Nginx 緩衝均可能影響結果。圖中不將 UAF 畫成必要步驟，因目前資料無法證明它與這條鏈之間的實際因果。

  1. 建立假設

    依首頁提示與 PHP 版本，拆分記憶體安全風險、Session 寫入面及檔案包含面，分別核對前提。

  2. Session Injection

    在課程情境中，由客戶端影響 Session 識別與上傳進度資料，讓受控示意內容進入 Session 儲存；不在此保留實際內容或請求格式。

  3. 確認資料可達性

    釐清 Session 儲存處理器、有效路徑、存取權限與清理時機。若資料已清除或不可讀，後續包含便無法依此方式成立。

  4. LFI 觸發

    view.php 的不安全路徑選擇將 Session 檔案當作可包含資源，跨越「不受信任資料」與「應用程式碼」的邊界。

  5. 驗證 RCE 與 flag

    以最低限度、非破壞性的結果確認 PHP 執行能力；依學員敘述完成授權 flag 驗證。RCE 不代表 root 權限或容器逃逸。

06 / POST-EXPLOITATION

權限取得後行動

依練習情境，容器缺少 ps、netstat 等工具。工具不存在並不代表系統資訊無法取得：Linux 的 /proc 由核心動態提供行程與網路狀態，PHP 的 file_get_contents 可讀取可存取的檔案，scandir 則可列出可讀目錄；兩者不必啟動外部 shell。

  • 行程資訊：概念上先列舉 /proc 的數字目錄，再讀取對應的 status 或 cmdline。後者通常以空字元分隔；行程可能在兩次讀取間結束，讀取失敗不必然代表防護阻擋。
  • 網路資訊：/proc/net/tcp、tcp6 等內容是目前網路命名空間的核心表格，位址、連接埠與狀態碼須解碼；不能直接當成主機全貌，與行程對應也需額外資訊。
  • 檔案與環境：以 PHP 目錄列舉及檔案讀取能力辨識授權工作目錄、必要設定與驗證資源。flag 僅作成功判準，不保留真實值；未取得的 UID、路徑與輸出不在報告中臆造。

08 / REMEDIATION

修補建議

F-01｜升級 PHP，驗證所有工作行程已更新

將 PHP 8.3.35 升級至 8.3.36 或同分支更新的安全修補版；若遷移分支，官方對這兩項 CVE 列出的修補起點為 8.2.35、8.4.27、8.5.12。使用發行商套件時核對回補公告，更新容器映像並重新建立／重啟所有 PHP-FPM 工作行程。修補版本依據：PHP 官方變更紀錄。

php.ini 配套：無上傳需求可設 file_uploads = Off，並在 Nginx 拒絕不需要的 multipart 請求；依業務縮小 post_max_size、max_file_uploads 與輸入限制。這些措施縮小曝險面，無法取代更新，也不存在適用所有部署的單一 ini 修補開關。

驗收：由實際 FPM 執行環境確認修補版本與套件來源；在隔離 Lab 回歸測試，檢查工作行程與錯誤日誌。

F-02｜停用不需要的上傳進度追蹤

; php.ini 或對應 FPM 設定層；套用後重新載入工作行程
session.upload_progress.enabled = Off
session.upload_progress.cleanup = On

清理機制僅為配套，不能保證資料從未寫入或消除時間窗。若業務需要進度追蹤，應另行設計不被 PHP 包含邏輯讀取的資料通道。版本：一併套用 F-01 升級；升級不會自動消除此設定的應用風險。

驗收：確認 FPM 的有效設定已停用該功能，測試上傳不再建立對應的進度資料，且正常上傳功能仍可使用。

F-03｜拒絕未初始化的客戶端 Session ID

session.use_strict_mode = On
session.use_only_cookies = On
session.use_trans_sid = Off
session.cookie_httponly = On
session.cookie_samesite = Lax
; 正式 HTTPS 部署另啟用 session.cookie_secure = On

嚴格模式是主要控制；其他設定為防禦補強，無法修補 LFI。自訂 Session 處理器須實作相應 ID 驗證能力，登入及權限變更時也應重新產生識別碼。版本：依 F-01 升級，並重新確認處理器相容性。設定依據：PHP Session 設定手冊。

驗收：合法新連線仍能建立 Session，而不存在的客戶端指定 ID 不被直接採用；確認登入流程與 Cookie 行為正常。

F-04｜修正 view.php 的模板選擇邏輯

將輸入限制為固定的頁面識別碼，由伺服器端白名單映射至固定模板；禁止把使用者提供的路徑直接傳入包含函數。若仍需處理路徑，應以正規化後的完整路徑確認目錄邊界，並拒絕白名單外的資源。

; 防禦配套，不能單獨阻止本地檔案包含
allow_url_include = Off
; session.save_path：設為獨立、非公開的專用目錄
; open_basedir：依實際應用配置最小可讀範圍後再套用

allow_url_include = Off 主要限制 URL 包含，無法阻止本地 Session 檔案被包含。若 open_basedir 同時允許 Session 與模板目錄，也不能切斷此鏈；Session 移出網站根目錄亦不等於不可被 PHP 讀取。根本修補仍是固定模板映射與資料／程式碼分離。版本：依 F-01 升級；應用 LFI 須另外修正。參見 open_basedir 手冊與URL 包含設定。

驗收：白名單頁面正常顯示；任意路徑、Session 檔案與其他非模板資源皆遭拒絕，拒絕事件可追蹤且不揭露敏感路徑。

修補優先順序：優先更新 PHP 並封堵 LFI，再收斂 Session 設定與可讀檔案範圍。於隔離 Lab 保存修補前後的去識別化證據，指派負責人並完成回歸驗收；Nginx、FPM 與應用日誌以請求識別碼關聯，避免記錄 flag 或完整 Session ID。

09 / CONCLUSION

結論

依學員回報，本次 PHP2Shell Lab 練習完成 Session Injection、LFI、RCE 與 flag 驗證。核心教訓是：原本僅供儲存狀態的 Session 資料，一旦被不安全的包含邏輯當成程式碼，就能跨越信任邊界；缺少系統工具也無法阻止透過 PHP 與核心介面進行探勘。

報告應分別記錄「官方確認的記憶體缺陷」、「靶機設定與應用缺陷」及「學員回報的成功結果」。目前證據可支援練習流程留存，仍不足以宣稱兩項 CVE 都已在 PHP-FPM 上觸發。後續以去識別化請求／回應、有效設定與修補回歸紀錄補足證據，才能完成可重現的驗證。

學完這份報告，可以帶走三件事：
  1. 資料與程式碼要分開。使用者能控制的內容，不應該有機會被當成程式執行。
  2. 單一設定幾乎不會「直接」造成入侵，但組合會。本例的 Session 寫入、ID 偽造與檔案包含各自看似風險不高，合在一起就構成完整路徑。
  3. 版本更新與設定加固要一起做。升級 PHP 修補已知缺陷，再關閉不需要的功能，兩者互補。
